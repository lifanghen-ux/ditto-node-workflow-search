# AutomationBench：上一候选的公开执行反馈

本文件仅整理 Search 的公开任务、工具调用和得分。没有读取独立 Test、隐藏期望状态或评分断言。以下任务标识仅用于关联证据，不能写入候选代码做特判。由你根据证据提出一个连贯的机制假设，设计下一版完整 A 模块。

上一候选完整 200 题单次通过 197 题（98.50%），未超过目标 98.90%；需要至少 198/200。有效题共 1,184 次模型请求、3,527,236 token，题均 10.218 秒。本批生成、工程失败和预算中断的付费开销另计，不能冒充有效题的开销。

## 三道零分题

- `simple.sheets_log_sales_call`：任务明确提供 Date、Type、Contact、Notes、Outcome 以及表格和工作表标识。候选搜索 append API 后，直接按这个文本顺序写入五个单元格，未读取工作表实际表头或现有行。工具返回 updatedRows=1、updatedColumns=5、updatedCells=5，随后结束，最终零分。公开 append 工具实现按现有表头将位置数组映射为列值；成功写入只说明操作成功，不能证明列与目标语义一致。未读取隐藏表头或期望内容，不能断言具体是哪一列错了。
- `simple.zendesk_resolve_email`：公开任务要求将票据改成 solved 并给指定客户发送解决邮件。工具确认票据 status=solved；候选编码带 To、Subject 和正文的 RFC 邮件后调用 Gmail send，得到 SENT 和消息标识，最终仍为零分。候选未读取发送后的消息。公开轨迹未提供确切失败原因，不得臆造评分断言或把“接口返回成功”当成整题通过。
- `simple.demo_request_zoom_email`：候选读取客户来信，创建要求名称的会议，日期为 2026-02-28T15:00:00Z、时长30分钟；使用返回的 join_url 给来信地址发送邮件，工具返回 SENT，最终零分。候选未读取发送后的消息。不能仅凭零分就认定会议、收件人、编码或时区中的某一项必然有错。

## 已通过但代价高的题

- `simple.hs_create_deal_with_contact`：30次模型请求、239,948 token。关联接口多次返回相同的 `No handler for PUT .../associations/contact/.../3`；候选反复搜索相似关键词、多次重发同一失败请求，达到自身30轮上限。完整累积 transcript 和多次扩大 top_k 使后续每次请求继续增大。题目最终得1分只代表现有评分结果，不证明反复失败的操作有效，不能通过利用宽松评分来设计候选。
- `simple.email_sf_contact_account_update`：29次模型请求、165,813 token。候选曾对未找到的 Account 进行 PATCH，读取后仍见旧关联，多次查询和搜索，之后才创建新 Account 并更新 Contact.AccountId。公开观察表明读取的最新状态需要真正影响后续决策。

可以检验的方向包括更准确地理解工具 schema 和当前状态、避免无信息增益的相同失败动作、保留精确必要信息的紧凑状态、仅在有价值时验证实际写入。它们是备选假设，不是固定节点顺序；是否采用、如何组合、是否需要额外模型调用以及何时停止，由你的 A 模块自主设计。优先修复有依据的质量缺陷，同时比较实际请求、token 和时间，不能只靠缩短文字或换节点名称宣称优化。

继续使用现有工具和官方模拟环境；不扩展或修改适配器。不要按任务ID分支、写死答案、访问评分器、私有世界状态或文件系统。生成的模块必须适用于当前数据集中的一般任务。
